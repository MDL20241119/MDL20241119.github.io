# 横のエレベーター：GitHub Pages体験デモ

## 0.18.0：3役のUX改修（公開前の確認版）

ユーザーは1人を見える状態で初期選択。乗る場所→降りる場所でCore確認画面が開き、最後の明示確認まで3タップ。前回の完了した移動は2タップ。地図・LINE風チャットは連動し、入力だけでは予約を保存しない。

ドライバーは地図・次の乗降場所・ナビ・停車確認を中心に配置。引受済みの自車両の依頼を「乗車中の降車→到着済み→引受順」で番号表示する。目安順であり最短経路の最適化ではない。選択中の依頼が乗車済みになると、ナビ先が降車地点に変わる。Google マップへ渡すのは架空地点の座標のみ。未引受・終了時にはリンクを出さない。

管理者は現在の配車稼働率・乗車率、期間の受付・完了・人数・取消、完了率、平均待ち時間、日別・時間帯・乗降ルートを表示。今日・7日・30日で切替。保存済みイベントの時刻を使う。

時間稼働率は分析用の稼働時間帯を設定したときだけ計算。引受〜完了／取消の記録時間を、登録車両数×経過済み稼働枠で割る。同じ車両の重複時間は結合し、日本時間の日付境界・夜間跨ぎに対応。未設定・分母ゼロを0%と表示しない。実走行センサーや正式な運行計画の取得ではない。過去の車両増減は考慮せず、現在の登録車両を分母に使う。

集計は取得済みの最新200件が上限。到達時は部分集計と表示する。受付は作成日、完了は降車日、取消は取消日、平均待ち時間は乗車日。完了率は完了÷（完了＋取消）で、進行中は含めない。時刻不足の記録は時間計算から除外して件数を示す。分析設定は運行の受付時間を変えない。

ナビの仕様：[Google Maps URLs](https://developers.google.com/maps/documentation/urls/get-started#directions)。端末位置とターン案内はGoogle マップ側で扱う。架空地点なので実送迎には使わない。

検証：ユーザー29項目、運行管理31項目、集計・順序・ナビ境界値15項目、合計75項目が合格。結果は `tests/yoko-demo/ux-*-result.json`。実機・最新CSSの公開ブラウザー確認は未完了。既定mainへのpushが自動承認レビューで拒否されたため、確認用ブランチでレビュー後に公開する。

## 0.17.0（旧版）：マニュアルと同じ、地図からチャットへ続くスマホ体験

ユーザー画面はPCでも最大540pxのスマホ型に統一し、「地図が上、LINE風チャットが下」の一続きの画面に戻した。場所は地図でも文章でも選べ、人数は大きな3択で入力できる。地図とチャットを切り替えるメニューは使わない。場所と人数がそろうと下部に大きな確認ボタンを表示し、元のCore確認画面を開く。入力途中はチャット欄を隠さない。入力例は内容を埋めるだけで、依頼は確定しない。

依頼後は同じ受付番号をドライバー役で体験できるボタンを表示する。ドライバーの初期選択はこの依頼を優先するが、Coreから返された担当範囲の依頼だけを対象にする。地図・受付・黄色の処理待ち、乗車→降車カード、次の操作を縦の流れにまとめ、停車の再確認と確定画面を維持する。降車後は管理者の記録へ進める。

管理者は待ち件数・人数と地図、状態別の一覧、車両の状況を表示する。「引受待ち・運行中・完了／取消・すべて」で絞り込める。検索チャットと詳しい記録は必要なときに開ける。3者とも、元の確認・取消・競合確認・権限の仕組みを使い、Core・初期データは変更していない。

自動試験は実際のPyodide CoreとJSDOMで52項目（ユーザー25、運行・管理27）に合格。入力例の無副作用、固定ボタンからの確認、今回の依頼の引継ぎ、取消、他画面の更新による確認失効などを検証。結果は `tests/yoko-demo/manual-journey-result.json` と `manual-operations-result.json`。JSDOMは見た目や実機キーボードを検証しない。

`--ui-only` は既存のCoreバンドル・初期DBを保ってUIを生成する。テストにはjsdomとPyodide 314.0.7が必要。

## 0.15.0：3画面をNeo Swiss・大きな文字に統一

ユーザーは従来の地図・チャット入力を維持。ドライバーはマニュアルと同じ「地図／受付／処理待ち／運行確定」の構成で、乗車・降車を矢印カードに表示する。管理者は地図、現在の待ち、車両別の状況を一画面に整理する。白地と罫線を基調に、水色・黄色・ピンクで役割を区別。主な本文は18px、主要操作は高さ52〜66px以上を基本とし、小画面でも文字を縮小しすぎない。デスクトップは横長のグリッド、スマートフォンは縦に並べる。

3役のチャット欄は左に案内、右に入力、白と緑の吹き出し、青い背景のLINE風表示。表示時刻はこのブラウザーでメッセージを表示した時刻。既読状態は表示しない。LINE接続や外部AIは利用していない。

ドライバーと管理者は地図ピン、場所名、受付番号、「処理待ち」「運行中」「履歴」で対象を探せる。ドライバーの引受・到着・乗車・降車は、停車確認と操作確認画面を経て元のCoreへ渡す。依頼の版が変わると確認画面を取り下げる。管理者のチャットは閲覧用で、運行状態を変更しない。例外の「乗せられない」「乗せる人がいない」は連絡手順の案内であり、例外報告の送信・取消は未実装。巡回順最適化、車両位置・到着予測、日報・月報出力はこの画面更新では追加していない。

管理者の「引受待ち」は未引受の依頼件数、「乗車を待つ人」は引受前・迎車中・到着後の人数を合計する。完了・取消・車両ごとの人数は取得した最新200件から計算し、日次の全件集計とは表示しない。

入力とユーザー操作の17項目に加え、3役の状態共有、確認前の無副作用、二重操作、他画面の取消との競合、チャットのHTML無効化など20項目を `tests/yoko-demo/operations.test.cjs` で検証する。どちらも実際のPyodide Coreを利用する。公開画面での地図・チャット・3役の運行操作と320px表示の確認記録は `tests/yoko-demo/neo-browser-result.json` を参照。

## 0.14.0：地図とチャットの入力

ユーザー画面は、手順表示→地図とチャット→内容確認→車両確定の流れ。地図のピン、チャット候補、文章入力、人数ボタンは同じ入力内容へ反映する。例：`中央広場から駅前ロータリーへ2人`、`目的地はふれあいセンター`、`2人`。一つ戻る・選び直す・依頼内容の変更にも対応する。

チャットは登録地点を照合するローカルの入力補助で、外部AI・ジオコーディングへの送信はない。不明な場所・同じ乗降場所・範囲外の人数・曖昧な入力は確定せず案内する。入力しただけでは保存しない。元のフォームからCoreの確認ドラフトを取得し、利用者が確認ボタンを押したときだけ依頼を保存する。

地図は既存の `oita-mobility/assets/leaflet.js` / CSS（Leaflet 1.9.4、同ディレクトリにライセンス）を利用する。[国土地理院の淡色地図](https://maps.gsi.go.jp/development/ichiran.html)を表示するが、3つの乗降場所の名称・座標は架空のデモ設定。実在施設の住所・乗車位置を示さない。破線は地点の組合せのみで、経路計算ではない。位置情報は要求しない。背景タイルの取得時は地図の表示範囲と通常のアクセス情報が国土地理院へ伝わる。

引受後の車両確定・到着・乗車は保存済みのCore状態に連動する。車両写真や到着予測を捏造しない。添付マニュアルの写真は再配布していない。

入力解析と画面→Coreの17項目を `tests/yoko-demo/journey.test.cjs` で確認済み。`NODE_PATH` にjsdomとPyodide 314.0.7を配置して実行する。公開画面でも、地図とチャットを組み合わせた依頼→引受→車両確定表示→到着→乗車→降車を確認済み。390px・320pxの表示領域で横はみ出しがなく、3つの地図ピンが表示範囲内に収まることを確認した。記録は `tests/yoko-demo/journey-browser-result.json`。実機のスマートフォンやSafariでの試験は含まない。

ユーザー、ドライバー、管理者の3画面を、架空の地域・車両・アカウントで体験する公開デモ。実際の送迎、料金請求、外部通知は発生しない。

- ユーザー入口：`./?role=user`
- ドライバー入口：`./?role=driver`
- 管理者入口：`./?role=admin`

同じブラウザーのIndexedDBに保存する。Web Locksで同一ブラウザー内のタブを直列化し、各処理前後にIDBFSを同期する。別端末・ブラウザー間の共有、本番の本人認証は含まない。入口の選択は認証ではない。

## 共通業務処理

`core-bundle.json` はローカルWebアプリ0.12.0のPython業務モジュールをそのまま含む。各ファイルのハッシュと出典コミットを記録。変更したのは架空fixtureの表示名のみ。予約の確認、権限、席数、状態遷移、取消、操作IDと冪等性はCoreが判断する。JavaScript側に予約ルールを作り直していない。

Pyodide 314.0.7 / Python 3.14.2をWeb Workerで実行する。公式配信先 `https://cdn.jsdelivr.net/pyodide/v314.0.7/full/` に固定し、`tzdata` 2025.3を追加する。公式情報：[Web Worker](https://pyodide.org/en/stable/usage/webworker.html)、[永続化](https://pyodide.org/en/stable/usage/file-system.html)。

PyodideにはOpenSSLのPBKDF2が含まれないため、初期の架空アカウントDBだけは、変更していない元の `app.db.initialize` をネイティブPythonで実行して生成する。パスワードハッシュの計算を弱めたり代用したりしない。DBには本番の秘密・セッション・予約・個人情報を含めない。圧縮した初期DBのSHA-256を確認して展開し、最初の架空の受付と完了履歴は実行時にCoreの通常操作で作る。

`demo_runtime.py` は公開された3つの架空actorに入口を対応付ける薄いアダプター。公開サーバーの認証・認可の代わりとして流用しない。各画面のAPI呼出は `demo-bridge.js` がブラウザー内のCoreへ渡す。GitHub Pagesには予約APIを立てない。

## 再生成と試験

```sh
python3 scripts/yoko-demo/build.py --source /path/to/yoko-elevator
npm install --prefix /tmp/yoko-demo-test pyodide@314.0.7
NODE_PATH=/tmp/yoko-demo-test/node_modules node tests/yoko-demo/run-wasm.cjs
node --check danchi-elevator/demo/demo-worker.js
node --check danchi-elevator/demo/demo-bridge.js
node --check danchi-elevator/demo/app.js
```

WASMの受入試験は実際のPyodide上で、3役・操作確認・停止確認・全乗降・取消・他人の参照拒否・二重送信を検証する。DOMや実ブラウザーでの検証とは別に結果を記録する。

LINEは後工程。国交省・直接API・MCP・A2Aは全体要件として維持するが、公開デモで外部接続・全面適合を表明しない。商用本番のアカウント管理、サーバー共有、正式運行設定・写真・通知・配車相手は元のWebアプリの公開条件に従って別途実装・受入する。

デモ本体と専用の生成・試験ファイルだけを追加し、既存HP・カタログ・他の交通アプリのファイルは変更しない。公開リポジトリへの配置を包括的なオープンソースライセンス付与と扱わない。
