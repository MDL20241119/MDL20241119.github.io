# e-Palette ONE｜2026-10-13 手入力MVP

現MVPの優先仕様は「車両APIなし・残量手入力」。9月公開版を継承して10月10日の手入力版を統合した。新規の別アプリではない。実車接続を現MVPの必須条件から外すが、通常API・MCP・A2A・交通標準連携は廃止しない。

## 最初に使う

1. 公開入口 `/` で「利用を計画 → 現場を確認 → 次の人へ」を試す。体験はタブ内の模擬データだけ。
2. 「チーム」からサインイン。以前の本人用D1保存は「自分の保存した体験」に残る。
3. チーム名と1〜3台を選んで、空の業務台帳を作る。架空の予約・在庫・観測値を持ち込まない。
4. 「その他 → 運用設定」で確認期限の根拠、実車の電池・充電条件、充電場所、担当資格、共用設備を設定する。未設定では開始可と判定しない。
5. 管理者が役割を選んで招待コードを作成する。担当者は自分のアカウントで参加する。コードは24時間・1人限り。コードの送信は自動では行わない。

## 一日の流れ

| 段階 | 実装した操作 | 次へ進む条件 |
|---|---|---|
| 計画 | 3段階の入力、用途選択、下書き、申請、理由付き差し戻し | 利用日時・場所・人数・電力条件が保存されている |
| 割当 | 管理者が車両・現場担当・返却受領者を確定 | 最新版で車両・人・設備・前後の準備時間・資格を検証 |
| 準備 | 充電逆算、充電枠、清掃・設営・整備・回送などの担当・期限 | 受領と完了を分離し、残件を管理 |
| 開始前 | 残量・時刻・確認者・場所・プラグ・異常・距離を一度に記録 | 有効な手入力、現場情報、担当本人、資格、チェック、準備完了 |
| 利用中 | 乗車・降車、配車、注文・在庫・15分受取枠・受渡し | 各状態を独立。支払・返金には現地の確認根拠を残す |
| 異常 | 報告・使用保留・影響予約・連絡記録・予定変更・復旧 | 新しい現場確認と管理者／安全確認者の根拠 |
| 返却 | 返却時の観測、申請、本人受領、再割当、理由付き代理受領 | 未降車・未受取を解決。受け手を明確にする |
| 次利用 | 準備と最新状態を再判定して貸出可能を記録 | 返却済みだけで完了しない。場所不明・プラグ接続中は拒否 |

現地入金の記録は外部決済の実行ではない。利用者への連絡記録は自動通知・相手の受領を意味しない。配車確定は走行開始ではない。

## UI/UX

- 「今日／予定／車両／その他」の4メニューを維持。スマートフォンでは下部ナビ。
- 初めての人に3つの入口を提示。入力・確認・記録の手順を表示する。
- 車両ごとに「見込み／対応／利用不可／確認不可」を文字とアイコンで区別する。
- 観測の日時は秒まで保持。表示は日本時間。日付をまたぐ予定も対象日に表示する。
- 保存中／保存済み／入力未保存／送信結果不明を表示。未保存入力を閉じる前に確認する。
- 主操作は64px、フォームの文字は18pxを基準とする。文字拡大、狭い画面への折返し、フォーカス表示、読み上げラベルを維持。
- 実ブラウザーでの200%拡大、スクリーンリーダー、タブレット、高齢者の操作試験は今回未実施。実機適合・WCAG全面適合とは呼ばない。

## データと権限

`organizations` / `memberships` / `invitations` を追加するスキーマのみの移行。既存のworkspaces・receipts・auditは削除／上書きしない。選択した組織IDは認証ではなく、すべての読取・変更・CSVで所属を照合する。

役割：管理者、安全・復旧確認者、運転・現場担当、充電・準備担当、利用申請担当、閲覧のみ。開始・返却は割当本人。作業の受領・完了は担当本人。管理者の代理は理由を記録する。組織メンバーの利用停止時には委任キーも解除する。

APIの操作キーは認証主体ごとに分離。JSON状態・操作受領・監査をD1の原子的なbatchで更新し、版違いを409で拒否する。応答消失時は同じキーで再送する。端末キューはアカウントと組織の両方で分離し、送信時にも保存先を照合する。

匿名の管理画面と残量専用画面は同じタブ内台帳を使う。写真と送信履歴はIndexedDBに残すが、匿名ではタブ別、本人用ではアカウント＋組織別の名前空間を使用する。写真は任意・端末内のみ。7日保持は試験設定で、次回の読込時に期限を判定する。共同写真共有は未実装。

業務モードの時計はサーバー現在時刻。模擬値、自動取得、検証時計の前進、体験リセットは実業務へ昇格できない。観測・現場確認は利用／充電後に失効し、停車しただけで復活しない。

## 検証の位置づけ

旧domain22件、連携30件、guest/UI12件、手入力25件、キュー9件、SQLite4件を回帰対象とする。追加の業務シナリオ、実際のAPIハンドラー＋SQLite D1代替、Reactサーバー描画を確認する。今回の結果は合計139件合格、失敗0件。TypeScript型検査も合格。実行結果は `tests/results/manual-mvp/`。

API試験は本物のルート処理とSQLを使うが、認証ヘッダーとD1バインディングはテストプロセス内だけの代替。実D1、ホストのログイン、2台の実端末の同時操作の試験ではない。`tests/service-mocks.mjs` はテスト専用であり、本番コードから参照しない。

## 連携・残る現場検証

- 通常API・MCP・A2Aは同じ選択組織・業務Coreを使う。本人承認・内容・期限・データ版の確認を継承。
- COMmmmONSは19操作中10操作の限定実装。採用版・原本ハッシュは維持。GTFS Schedule限定、Realtime・QR認証ハブ未接続。
- 正式な運行サービスの設定がない業務チームでは、体験用の停留所・運賃・便を実運行として外部公開しない。
- 実車制御、オンライン決済、外部通知送信は実施しない。実車・外部AI・交通事業者・QR認証ハブの実接続は未確認。
- 公開後、現場責任者が車両別根拠と鮮度基準を設定し、複数アカウント・実機・充電実測で最終確認する。
